# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Visión general

**Dfiru POS** — sistema punto de venta para pizzería (producción activa, dominio `d-firu.com` tras Cloudflare Tunnel). Cuatro apps:

| App | Stack | Propósito |
|-----|-------|-----------|
| `Backend/` | NestJS + PostgreSQL + Redis | REST API + WebSocket gateway |
| `Frontend/` | Expo 55 · Expo Router (RN + web) | POS principal para el staff |
| `RiderApp/` | Expo 56 (RN puro) | App de domiciliarios (solo lectura de sus entregas) |
| `ClientWeb/` | Vite + React (web puro) | Pedidos de clientes finales: login, crear orden, nosotros |

Workspaces npm: `Frontend`, `Backend`, `RiderApp` (y `Desktop`, declarado pero sin carpeta). **`ClientWeb` NO es workspace** — tiene su propio `node_modules`/lockfile y no importa nada de `Frontend/src/shared`.

El código compartido entre Frontend y RiderApp (tipos, API client, hooks, contextos) vive en `Frontend/src/shared/`, importado vía el alias `@/src/shared`. RiderApp lo resuelve con paths en su `tsconfig.json` (`@/src/shared` → `../Frontend/src/shared`) + `metro.config.js` que observa la raíz del monorepo.

## Configuración de entorno

- **Backend (`Backend/.env`)**: copiar de `.env.example`. Críticos: `DATABASE_*`, `REDIS_*` (BullMQ + Socket.io adapter), `JWT_SECRET` (≥32 chars), `CORS_ORIGINS` (separados por coma; incluye `http://localhost:5173` para ClientWeb), `MAIL_*` y `REPORT_EMAIL` para reportes de cierre. Puerto por defecto **3000**. **Docker**: `Backend/Dockerfile` es multi-etapa (`builder` → `production` con solo `dist` + dependencias de producción; `development` opcional). `docker-compose.yml` usa `target: production` (sin bind mount ni `start:dev`): tras cambiar código del backend hay que `docker compose up -d --build backend`.

- **Docker Compose (`.env` raíz)**: `DB_PASSWORD`, `JWT_SECRET`, `EXPO_PUBLIC_API_BASE_URL`, `CORS_ORIGINS`, `CLOUDFLARE_TUNNEL_TOKEN`.
- **Versiones**: root `overrides.react = 19.2.3`. Frontend usa Expo 55/RN 0.83; RiderApp Expo 56/RN 0.85 — **la versión de RN va atada al SDK de Expo; no unificarlas via overrides**.

## Arquitectura

### Singleton axios compartido (crítico)

`Frontend/src/shared/services/api.ts` crea el singleton `http` (axios) y `api = createApi(http)`. El `AuthProvider` compartido (`Frontend/src/shared/contexts/AuthContext.tsx`) inyecta el header `Authorization` y monta el interceptor de refresh 401 **sobre ese singleton**. `Frontend/services/api.ts` no crea instancia propia: configura el `baseURL` del singleton (`setApiBaseUrl(http, getBaseUrl())`) y lo re-exporta. **Nunca crear una segunda instancia de axios en el Frontend** — las pantallas quedarían sin token tras el login (bug que ya ocurrió). RiderApp usa el mismo singleton vía `@/src/shared`.

### Shared (`Frontend/src/shared/`)

- **Tipos**: `types/models.ts` — fuente de verdad única del frontend. Deben mantenerse congruentes con las entidades/DTOs del Backend.
- **Barrel** `index.ts`: solo **named exports** (nada de `export *` — rompe tree-shaking). Al añadir símbolos nuevos, exportarlos explícitamente.
- **API client**: factory `createApi(http)` con métodos namespaciados (`api.auth.*`, `api.ordenes.*`, `api.facturas.*`, `api.domicilios.*`, `api.productos.*`, `api.empresa.*`, `api.cierres.*`, etc.). Los métodos ya retornan el `.data` de axios — no acceder a `.data` en las pantallas.
- **Contextos**: `ApiContext` (`useApi()`), `AuthContext` (AsyncStorage + refresh; el Frontend lo consume vía el wrapper `Frontend/contexts/AuthContext.tsx` que añade `useAuthNavigation` con redirects por rol), `OrderContext` (slots del formulario de orden), `OfflineQueueContext`, `ToastContext`.

### Backend (`Backend/src/`)

**Módulos**: `auth · ordenes · ordenes-productos · facturas-ventas · facturas-pagos · caja-movimientos · clientes · domiciliarios · domicilios · productos · pizza-sabores · inventario · estadisticas · contabilidad · cierres · empresa · common`.

**Auth**: `JwtAuthGuard` + `RolesGuard` + `ContadorGuard` + `ClienteGuard` globales via `APP_GUARD` (en ese orden) — toda ruta exige JWT salvo `@Public()`. Roles: `admin, cajero, cocina, mesero, domiciliario, cliente, contador`.
- **Contador**: rol de SOLO LECTURA limitado a contabilidad. `ContadorGuard` bloquea todo método ≠ GET y toda ruta fuera de `/contabilidad`, `/estadisticas`, `/facturas-ventas`, `/facturas-pagos`, `/empresa/cuentas-transferencia` (GET de cuentas; ya NO es `@Public`: solo staff autenticado, la prueba está en `acceso-publico.spec.ts` y `contador.guard.spec.ts`). En el POS solo ve Contabilidad y Analítica (menú exclusivo en `Navbar.tsx` + redirect en `useAuthNavigation`).
- **Staff**: login por username (`POST /auth/login`); `JwtStrategy` valida contra tabla `users` por `sub` (uuid).
- **ClienteGuard**: un token cuyo único rol es `cliente` solo puede usar la lista blanca `CLIENTE_ALLOWED_ROUTES` (hoy `POST /ordenes`) más las rutas `@Public`. Para exponer otra ruta a ClientWeb hay que añadirla ahí. `ClientesController`, los GET de `/ordenes` y `/estadisticas` ya NO son públicos (regresión cubierta por `test/unit/auth/acceso-publico.spec.ts`); el socket `/ordenes` rechaza tokens de cliente.
- **Clientes finales**: `POST /auth/cliente/login` y `/auth/cliente/registro` (públicos, teléfono + password); el token lleva `sub = teléfono` y rol `cliente`, y `JwtStrategy` lo valida contra la tabla `clientes`. `POST /ordenes` admite rol `cliente` con hardening (fuerza `tipoPedido='domicilio'` y `telefonoCliente` del token).
- `GET /domicilios/me` matchea `telefonoDomiciliarioAsignado = user.username` — los usuarios domiciliarios deben tener `username = teléfono` (así los crea el seed).

**Base de datos**: TypeORM + PostgreSQL, timezone `America/Bogota`. **`synchronize: true` corre también en PRODUCCIÓN y no hay migraciones de esquema**: solo cambios ADITIVOS en entidades (tablas/columnas nuevas nullable o con DEFAULT). Quitar o renombrar una propiedad, o cambiarle el tipo, BORRA la columna al arrancar; las columnas en desuso se dejan mapeadas como `@deprecated`. Las tablas de entidades eliminadas del código quedan intactas. Antes de desplegar, correr `npm run schema:preview` (con `DOTENV_CONFIG_PATH` apuntando a una copia restaurada de producción) y verificar que no haya `DROP` inesperado; el log de arranque muestra el DDL aplicado (`logging: ['schema']`). Nunca usar `npm run db:down` ni `backend:local` en el equipo de producción (`db:down` borra el volumen `pizzeria-pgdata`). Columnas decimales usan `NumericTransformer` (`common/utils/numeric.transformer.ts`). Fechas por día con `getBogotaDayBoundaries` (`common/utils/date.utils.ts`).

**Migraciones de DATOS** (`common/migraciones-datos/`): backfills y copias que synchronize no hace. Registro estático ORDENADO en `pasos/index.ts` (ids versionados, nunca reutilizar uno desplegado); cada paso queda en la tabla `migraciones_datos` (`ok|error|en_progreso` + `resultado` jsonb). Pasos `sync` corren en una transacción durante el arranque; pasos `background` por lotes idempotentes tras el arranque (marcan cada fila procesada). Advisory lock por transacción; apagado de emergencia `MIGRACIONES_DATOS_OFF=1`.

Pasos actuales, EN ESTE ORDEN: `productos-categoria-v1 → sabor-grupos-v1 → cuentas-factura-id-v1 → facturas-montos-v1 → inventario-unificado-v1 → ventas-detalle-v1` (el único `background`). **`sabor-grupos-v1` va ANTES de `ventas-detalle-v1`** (el parser asigna cada sabor al grupo Pizza o Calzone: pizza y calzone comparten nombres como "Carnes"; `esCalzone` en `SaborCatalogo` desempata y `pasos-facturacion.sql.spec.ts` vigila el orden). `cuentas-factura-id-v1` enlaza por id las facturas que solo guardaron el nombre de su cuenta; `facturas-montos-v1` completa `monto_pagado` y el reparto efectivo/QR de las pagadas antiguas (nunca pisa un valor, ningún total cambia). `manager.query` de un `UPDATE/DELETE … RETURNING` devuelve `[filas, n]`, no un conteo: usa `contarActualizadas` (`migraciones-datos.utils.ts`).

**Migración de producción** — runbook paso a paso en `MIGRACION-FACTURACION.md` (raíz). Herramientas de SOLO LECTURA (la sesión abre con `default_transaction_read_only = on`) en `common/migraciones-datos/herramientas/`: `npm run migracion:auditar | migracion:linea-base | migracion:verificar | migracion:precios` (ts-node, leen `DATABASE_*` de `.env` o de `DOTENV_CONFIG_PATH`); compiladas corren con `node dist/common/migraciones-datos/herramientas/cli.js <cmd>` dentro de la imagen de producción. Flujo: respaldo → auditoría (los `BLOQUEANTE` hacen fallar el arranque: domicilios con repartidor que no existe en `domiciliarios` o que solo consta en la columna heredada `"domiciliarioTelefono"`; `synchronize` es transaccional, así que un fallo no deja la base a medias) → línea base con el backend viejo DETENIDO → arranque → `verificar --base … --esperar`. El ensayo completo (estructura anterior de `Backend/init.sql` + datos con anomalías → auditoría → bloqueantes → línea base → DDL → 6 pasos → verificación) está en `test/unit/migracion/`; si cambian las entidades, regenera `fixtures/sincronizacion-desde-estructura-anterior.sql` (foto de `schema:preview`). Si añades o cambias un paso, actualiza auditoría, verificación y ese test. Trampas ya vividas: (1) el `docker-compose.yml` anterior corría el backend en modo watch con el código montado (`./Backend:/app` + `start:dev`): traer código nuevo con el contenedor arriba ejecuta `synchronize` y las migraciones sin respaldo — detenerlo ANTES; (2) no dejar archivos `.ts` sueltos en la raíz de `Backend/` (p. ej. un script de ensayo): `tsc` cambia la raíz común y la salida pasa a `dist/src/main.js`, rompiendo el `CMD node dist/main.js`; (3) `Backend/package-lock.json` está desactualizado, por eso el Dockerfile usa `npm install` y no `npm ci`; (4) los respaldos van en `backups/` (ignorado por git y por Docker: datos reales de clientes); (5) `Docs/` está en `.gitignore`, por eso el runbook vive en la raíz. **Cambio de servidor / formateo** (§12 del runbook): `scripts/respaldar-servidor.ps1` (dump comprimido + SQL plano + conteos por tabla + SHA-256 + `.env` + inventario del equipo, con `-Verificar` restaura en una base temporal y compara) y `scripts/cargar-respaldo.ps1` (se niega a pisar una base con ventas sin `-Forzar`; compara filas con el origen); `scripts/probar-scripts.ps1` los prueba (junto con `docker-local.ps1`) con un `docker` simulado y NO ejecuta Docker. Trampa: la primera vez que arranca el contenedor `db` con un volumen vacío crea `appdb` con `Backend/init.sql` + `Backend/seed-menu.sql` (estructura vieja y menú de ejemplo), por eso la carga borra y recrea `appdb` antes de restaurar; y `pg_isready` por socket (el healthcheck) puede dar «listo» durante esa inicialización, por eso el script espera por TCP (`-h 127.0.0.1`). Esos dos scripts deben correr juntos sin error: si `seed-menu.sql` falla, el entrypoint de postgres se corta a mitad, el contenedor se reinicia SIN repetir la inicialización y el primer `docker compose up` termina en «db is unhealthy» (pasó porque usaba `productos.personalizacion`, que `init.sql` no tiene: ahora la crea con `ADD COLUMN IF NOT EXISTS`, misma definición que la entidad). Al tocar cualquiera de los dos, `test/unit/migracion/primer-arranque.sql.spec.ts` los corre en ese orden en PGlite. En PowerShell 5.1: `"$nombre: …"` se interpreta como variable con ámbito (usa `${nombre}:`), `2>&1` sobre ejecutables convierte stderr en errores, y los `.ps1` con tildes necesitan UTF-8 con BOM.

**Ventas estructuradas**: además del texto `ordenes_productos.producto` (formato "Pizza - Grande (Paisa + Carnes)", que leen KDS/recibos — no cambiarlo), cada línea guarda `productoId` (columna `"productoObjProductoId"`, no renombrar), `producto_base`, `variante_nombre`, `tamano` (solo pizza), `categoria`, `precio_lista`, `precio_manual`, `detalle_version`, y sus sabores en `ordenes_productos_sabores` (`fraccion` = 1/n). En respuestas van como `saboresDetalle`: NO llenar `sabores`/`sabor1..3` (KDS, `printReceipt` y RiderApp los concatenan al texto y saldrían duplicados) ni crear un `productoNombre` por línea (lo prefieren sobre `producto` y perderían tamaño y sabores). El histórico se rellena con el paso `ventas-detalle-v1` (parser `ordenes/utils/parsear-linea-venta.ts`). `productos.categoria` (`pizza|calzone|bebida|jugo|adicion|comida|otro`, helpers en `common/utils/catalogo.util.ts`) y `ordenes.canal`/`usuario_creacion_id` alimentan los filtros de analítica. Definiciones únicas de dinero (venta válida, cobrado, por cobrar, método) en `common/domain/ventas.ts`, espejo en `Frontend/src/shared/domain/factura.ts`.

**Grupos de sabores** (`pizza-sabores/`, tabla `sabor_grupos`): las reglas de sabores son DATOS, no código — así un producto nuevo con sabores (hamburguesa, etc.) se configura sin tocar nada. Un `SaborGrupo` (Pizza, Calzone…) define `maxSabores`, `usaTamano`, `varianteEsSabor` (calzone: la variante ES el sabor, no se repite "- variante" en el texto) y el recargo por pedir varios sabores (`recargoExtraDesde` + `recargoExtra{Pequena,Mediana,Grande}`). Cada sabor (`pizza_sabores.grupo_id`, único por `(grupo_id, nombre)`) trae su propio recargo por tamaño (0 = no cobra; un grupo sin tamaños cobra solo la columna "grande"). Cada producto apunta a su grupo con `productos.saborGrupoId` y cada variante puede fijar su `tamano` (`pequena|mediana|grande`; null = se deduce del nombre, helper `ordenes/utils/recargos-sabores.ts`). El precio lo calcula SOLO `product-processing.service` con `calcularRecargoSabores` (mayor recargo entre los sabores + extra por cantidad), espejo en `Frontend/src/shared/utils/sabores.ts` y `ClientWeb/src/lib/sabores.ts` — mantener los tres congruentes. **Ya no existe tradicional/especial**: `pizza_sabores.tipo` queda mapeada como `@deprecated` (no quitar la propiedad: borraría la columna) y la fila `RECARGO_3_SABORES` es residuo (`findAll` la excluye). `productos.personalizacion` solo distingue 'jugo'/'ninguna' (los valores 'pizza'/'calzone' son heredados y cuentan como 'ninguna'); los sabores salen de `saborGrupoId`. API: `GET /sabor-grupos` y `GET /pizza-sabores[?grupoId]` públicos (ClientWeb), escrituras solo admin en grupos. El paso `sabor-grupos-v1` (sync, idempotente) crea los grupos Pizza/Calzone, asigna sabores y productos y deja los precios EXACTOS de antes (los tradicionales nunca cobraron recargo → se ponen en 0; entre "Paisa" tradicional y especial gana el especial y el otro queda inactivo sin grupo; extra de 3 sabores = valor de la fila de configuración, o 3000 donde estaba en 0). Antes de desplegar, `schema:preview` debe mostrar solo CREATEs de `sabor_grupos`/columnas nuevas y el `DROP INDEX` del índice único viejo de `pizza_sabores`. En el frontend hay un único selector de sabores (`components/orderForm/PizzaPersonalizadaModal.tsx`, dirigido por el grupo), un único editor (`app/(main)/gestion-sabores.tsx` + `SaborModal` + `GrupoSaborModal`) y un único selector "qué ofrece al pedirlo" (`PersonalizacionSelector`, usado también en `ProductModal`). La analítica filtra por `saborGrupoId` (`opciones.grupos`); sus filas de sabores traen `grupo`.

**Analítica** (`estadisticas/analitica/`, `GET /estadisticas/analitica/*`, `@Roles(Admin, Cajero, Contador)`): `resumen · productos · sabores · sabores/matriz · sabores/combinaciones · serie · horarios · mix · clientes · domiciliarios · opciones · calidad-datos`. Todos aceptan `FiltrosAnaliticaDto` (rango ≤ 366 días, `comparar`, listas separadas por coma); el SQL de filtros vive SOLO en `filtros.ts` (`ParametrosSql`, filtros de línea con `EXISTS` para no duplicar totales). Con `comparar` y un rango que incluye hoy, el período anterior se corta a la misma hora. `GET /estadisticas/resumen?from&to` (todo el staff) es la foto de dinero (ventas, gastos, balance) que usan `cierre-caja` y `CierresService`. **RiderApp — estabilidad y ubicación** (`src/lib/location.ts`): reglas que ya costaron bugs en producción —

2. El tracking **NO puede vivir en el `useEffect` de una pantalla**. Estuvo dentro de `DashboardScreen` y, como abrir Ajustes desmontaba esa pantalla, el cleanup apagaba el GPS: la pantalla que existe para arreglar permisos era la que rompía el rastreo. 3. Re-verificación en `AppState === 'active'` (con `ask:false` para no acosar con pop-ups): revive el servicio si el SO lo mató y recoge el permiso "Permitir todo el tiempo" que el usuario acaba de conceder en Ajustes del sistema — antes había que reiniciar la app para que surtiera efecto.
`ensureTracking` es idempotente (chequea `hasStartedLocationUpdatesAsync` antes de arrancar). La `SettingsScreen` muestra el estado real del servicio y permisos, y reintenta con `ask:true`. Todo el flujo está blindado con try/catch y la app envuelta en un `ErrorBoundary` propio (RN puro, no usa `@/src/shared/tw`). **RiderApp — GPS: más reglas aprendidas**: (4) En Android `distanceInterval` es un FILTRO, no un disparador extra: con 50 m un domiciliario parado dejaba de reportar; en Android va en 0 (un envío cada `timeInterval` aunque esté quieto) y 50 solo en iOS. (7) Diagnóstico: la tarea escribe `@Rider:gps` (`lib/gps-status.ts`: último envío exitoso y último error `sesion|red|otro`) y `useGpsEstado()` lo combina con permisos/servicio para decir POR QUÉ no se ve al domiciliario (cabecera de Entregas y Ajustes); `evaluarEstadoGps` es pura. (8) NUNCA usar `Linking.canOpenURL` para waze://, whatsapp://, google.navigation: (en Android 11+ devuelve false sin `<queries>`, y `android/` se regenera con prebuild): `navigation.ts` prueba `openURL` en orden con respaldo web. Diseño: minimalista (superficies planas con borde tenue, sin sombras ni brillos, tokens en `lib/theme.ts`), contenido centrado con `maxContentWidth` y las entregas pasan a 2 columnas desde `TWO_COLUMNS_FROM` (720 px).

**WhatsApp / n8n**: los flujos del bot de WhatsApp son workflows de n8n exportados en `workflows/` y `n8n/workflows/` (JSON, no código del backend). El bot crea órdenes por la API normal (con `metodo` de pago ya conocido) y `OrdenesGateway.emitirHandoffWhatsapp` emite `whatsapp:handoff` al POS.

**Background jobs**: BullMQ + Redis; cron `@nestjs/schedule`. Cierre automático a las **04:00** Bogotá (`CierresCronService`, `HORA_CIERRE`; único cron de cierre; cierra AYER —el día sigue siendo de medianoche a medianoche— y manda el correo): el local a veces atiende hasta las 2 a. m., así lo cobrado o editado después de medianoche sobre ventas de ayer entra al cierre. Al arrancar recupera el cierre de ayer, pero NO antes de las 4:00 (`antesDeHoraCierre`): un reinicio a la 1 a. m. no manda un cierre prematuro. Prueba: `test/unit/cierres/cierres.cron.spec.ts`.

### Flujo de negocio

- `POST /ordenes` → crea orden y `FacturaVenta` automáticamente. Contrato de items (referencia: `Frontend/components/orderForm/CreateOrderForm.tsx`): `{ tipo: productoNombre, varianteId (requerido), cantidad, sabor1..3?, base? }`. ClientWeb replica este contrato en `ClientWeb/src/lib/types.ts`.
- `PATCH /ordenes/:id/completar` → marca orden y factura pagadas (idempotency key).
- **Métodos de pago**: `'efectivo' | 'transferencia' (UI: "QR/Trans") | 'efectivo_transferencia' (UI: "Mixto")`. El desglose mixto vive en `pagoEfectivo`/`pagoTransferencia` de la factura.
- **Abonos** (`PATCH /facturas-ventas/:id/abono`): `AbonoDto { monto, metodo?: 'efectivo'|'transferencia', denominaciones?, cambioDenominaciones? }`. Acumula `montoPagado` y el desglose por método; al saldarse deriva `metodo` final (mixta si hubo ambos). Solo los abonos en efectivo generan movimiento de caja. Los abonos por QR guardan su cuenta (ver Cuentas de transferencia). El monto que envía el modal es **neto** (recibido − cambio).
- **Filtros por método**: helper compartido `matchesMetodoFilter` (`Frontend/components/ui/MethodFilterChips.tsx`) — "Efectivo" y "QR" incluyen facturas mixtas cuya componente sea > 0; "Mixto" es bucket propio. El `findAll` del backend aplica la misma semántica server-side (usado por balance-fechas).
- **Arqueo opcional** (`empresa_config.arqueo_caja`, default `true`; solo el admin lo cambia con `PATCH /empresa`, UI: `components/ui/ArqueoSwitch.tsx` en Ajustes del negocio, Balance del día y Gastos, hook `hooks/use-arqueo.ts`). Pensado para cuando el dueño atiende la caja: lo apaga, y al irse lo enciende y deja la caja contada. **Apagado**: el cobro en efectivo no se bloquea por falta de arqueo (`aperturaHecha` no se pasa a `FacturaCard`), `PaymentSelectionModal` muestra "Recibido / Cambio a devolver" pero no pide desglosar el cambio ni limita por billetes en caja, el efectivo se registra en pesos NETOS (`{coins: neto}`) y `CajaMovimientosService` no valida salidas/ajustes contra el conteo (`arqueoActivo()`; si falla leer la config se asume activo). **Siempre**: el saldo de caja parte del ÚLTIMO movimiento `apertura` del día (`desdeUltimaApertura`): un arqueo nuevo (botón "Nuevo arqueo") reemplaza la base y lo cobrado antes no se duplica; "arqueo hecho" = existe un movimiento `apertura` POSTERIOR a `empresa_config.arqueo_desde` (momento en que el admin lo volvió a encender; `EmpresaService.updateConfig` lo fija en cada apagado→encendido, `aperturaVigente()` en `use-arqueo.ts` lo aplica): al reactivarlo hay que contar la caja a mano, el formulario se abre solo y ese conteo pasa a ser el esperado. No es cualquier entrada. El prepago de `CreateOrderForm` (`PrepayPicker`) muestra "¿Con cuánto paga?" con montos rápidos, lo que ingresa y cuánto devolver — solo informativo (`recibido` no viaja al backend).
- **Caja y cobros de facturas de venta** (`CajaMovimientosService.compensarFactura / ajustarEfectivoDeFactura / efectivoNetoDeFactura`): revertir a pendiente, cancelar, borrar o cambiar el total de una factura cobrada en efectivo NO deja el dinero en caja — se compensa en la misma transacción con un movimiento de signo contrario (`"Reverso factura #N (motivo)"`). El neto se calcula sumando entradas − salidas ligadas por `factura_venta_id` (más las filas viejas de cambio, que se reconocen por su descripción `Cambio (abono )?factura #N`), así que es idempotente: repetir la operación no compensa dos veces. Toda ruta nueva que anule o reescriba un cobro debe pasar por ahí.
- **Cobro por transferencia/QR/mixto**: el servidor EXIGE la cuenta (`cuentaTransferenciaId`) en `completar`, `FacturasVentas.update` y abonos por transferencia, la valida contra `cuentas_transferencia` y guarda el nombre que dice la tabla, no el que mande el cliente. El POS offline (`OfflineQueueContext`) ya envía `cuentaTransferenciaId/Nombre`. Renombrar una cuenta reescribe las facturas viejas (intencional). `resolverCuenta` rechaza un nombre que no existe y una cuenta desactivada; reasignar toda la transferencia de una factura abonada a VARIAS cuentas se rechaza (se perdería el reparto). El POS NO preselecciona cuenta cuando hay más de una activa (`PrepayPicker`, `PaymentSelectionModal`): la elige el cajero; con una sola activa se marca sola.
- **Idempotencia de `completar`**: ya no depende solo de la `idempotencyKey` (el cliente la regenera en cada reintento): cobrar con la MISMA forma de pago una factura ya pagada no toca la factura ni la caja; con OTRA forma de pago es una corrección (`compensarFactura(..., 'cobro corregido')` y se cobra de nuevo).
- **Roles por endpoint**: `RolesGuard` solo exige rol si hay `@Roles`, por eso TODA ruta que escribe lleva `@Roles(...)` (única excepción a propósito: `POST /ordenes`, que usa también el cliente web). Dinero (facturas, gastos, caja) = admin/cajero (+ contador/mesero solo en lecturas de facturas-ventas); catálogo y domiciliarios = admin/cajero. `PATCH /domicilios/:id` admite `domiciliario`, pero ese rol solo puede cambiar `estadoDomicilio` de SUS entregas (`telefonoDomiciliarioAsignado === user.username`), si no → 403. `test/unit/auth/roles-endpoints.spec.ts` falla si aparece una escritura sin rol.
- **Editar orden** (`OrdenesService.update`): relee la orden después de actualizarla; si deja de ser domicilio borra su `Domicilios`, y el total se recalcula cuando cambia el tipo de pedido (domicilio ↔ otro).
- **Precios de sabores**: el cálculo vive en 3 sitios (Backend `ordenes/utils/recargos-sabores.ts` = verdad, `Frontend/src/shared/utils/sabores.ts` para el POS offline, `ClientWeb/src/lib/sabores.ts` solo para mostrar). Al cambiar una regla de recargo hay que tocar los tres: `test/unit/ordenes/recargos-paridad.spec.ts` los ejecuta con los mismos casos y falla si divergen.
- **Caja de gastos**: `cajaOrigen: 'principal' | 'gastos'`. Gastos con `metodo: 'efectivo'` mueven la caja de gastos; `'qr'` y `'efectivo_no_caja'` no.
- **Inventario unificado** (`Backend/src/inventario/`, `/inventario/*`): cajas y bebidas EMBOTELLADAS (gaseosa, agua, cerveza, otra) son `inventario_items`; jugos preparados y pulpas no llevan stock. Qué descuenta cada venta lo dicen las reglas `inventario_consumos` (variante → ítem × cantidad, `solo_para_llevar` para cajas) — ya NO se adivina por el texto de la línea (eso hacía gastar caja a "Coca Cola Personal"). `ConsumoOrdenService.reconciliar(ordenId, manager)` lleva el stock al consumo que corresponde a la orden TAL COMO ESTÁ: compara el objetivo (reglas × líneas; 0 si la orden o su factura está cancelada, o se va a borrar) con lo ya registrado en `inventario_movimientos` de esa orden y escribe solo la diferencia (idempotente; devuelve solo lo que de verdad salió). Se llama DENTRO de la transacción, después de escribir, en `OrdenesService.create/update/cancel/remove` y `FacturasVentasService.update(estado='cancelado')/remove` (antes del cascade); cualquier ruta nueva que cree o anule ventas debe llamarlo. Usa solo el `manager` recibido, corre en savepoint y nunca hace fallar la venta. El stock nunca baja de 0: vender sin stock queda como faltante (`delta` ≠ `aplicado`). Movimientos manuales: `entrada|salida|ajuste|conteo` (conteo fija el valor). Los datos se migraron con el paso `inventario-unificado-v1` (sync): su `resultado.fechaCorte` separa las órdenes viejas (descontadas por el sistema anterior, no se reconcilian); hasta que termine bien, `/inventario/*` responde 503 y las ventas no descuentan. Las tablas viejas (`inventario_cajas*`, `bebidas_movimientos`, `ingredientes_bebidas`, `variantes_ingredientes`) quedan intactas como respaldo y las columnas `*_bebida` de `producto_variantes` siguen mapeadas como `@deprecated` hasta la limpieza final.
- **Pantalla de inventario** (`Frontend/app/(main)/inventario.tsx` + `components/inventario/` + `hooks/use-inventario.ts`): pestañas Stock · Reglas · Movimientos. El estado `ok|bajo|critico` lo calcula el servidor (`estadoStock`). Reglas muestra las "auto" de la migración para revisar y avisa de pizzas/calzones sin caja (`GET /inventario/reglas/sugerencias`).
- **Precio manual por ítem** (Crear Orden): `CreateOrdenItemDto.precioUnitario?` opcional; cuando llega, `product-processing.service` lo usa tal cual y **NO** aplica recargos por sabor/base. El controller lo **descarta para el rol `cliente`** (no puede fijarse su propio precio). En el front vive como `OrderCartItem.precioOverride`; el carrito permite editarlo inline y restaurarlo.
- **Cotización copiable**: el `CartPanel` (Crear Orden) tiene "Copiar cotización" — arma el carrito actual como texto WhatsApp (`expo-clipboard`) con precio efectivo, para mandarle la cuenta al cliente antes de crear la orden.
- **Teléfonos colombianos** (`Frontend/src/shared/utils/phone.ts`): se guardan **siempre** en local de 10 dígitos. `normalizePhone` quita el `+57`/espacios al pegar (clave: `GET /domicilios/me` matchea `telefonoDomiciliarioAsignado` = `username`); `toDialablePhone`/`toWhatsappPhone` reañaden el indicativo solo para marcar/WhatsApp. RiderApp muestra el teléfono normalizado y tiene botón **Llamar**.

### Frontend (`Frontend/`)

**Routing**: Expo Router file-based bajo `app/(main)/`. Los `.web.tsx` son overrides web del mismo route; solo quedan donde el diseño es realmente distinto (`_layout` y `login`, que comparte la lógica vía `hooks/use-login-form.ts`). No crear un `.web.tsx` para cambiar un título: un solo archivo responsive con `useBreakpoint()`.

**Listas — regla clave**: en pantallas **nativas** usar `FlashList` v2 (`@shopify/flash-list` — ya **no existe** `estimatedItemSize`). En pantallas **web** usar `ScrollView` de `../../tw` con `className` — los componentes raw de RN (FlatList/FlashList) no reciben altura de la cadena flex vía className en web y colapsan invisibles (patrón documentado en `facturas.tsx` y `usuarios.web.tsx`). Items de lista siempre extraídos y envueltos en `React.memo`, con callbacks estabilizados en `useCallback` en el padre.

**Styling**: `Frontend/tw/index.tsx` exporta wrappers (`View`, `Text`, `ScrollView`, `Pressable`…) que aplican Tailwind via `react-native-css` — **importar de `../../tw`, no de `react-native`** (salvo estilos StyleSheet puros). NativeWind v5 / Tailwind v4; CSS vars (`--color-pos-bg`, `--color-pos-primary`) definen el tema oscuro POS. Estilos estáticos de items de lista en `StyleSheet.create`; dinámicos merged (`[styles.x, { width }]`).

**Receta visual única de tarjeta** (`styles/tokens.ts` + `components/ui/Card.tsx`): toda tarjeta nueva usa `<Card>` — fondo `white/.04`, borde `white/.07`, radio 16 (escala `radius` 8/12/16/24; nada de 14/20/28/40), padding 16, SIN sombra (`solid` = panel opaco para KPI/gráficas, `inset` = caja dentro de otra tarjeta). Lo que distingue a una tarjeta de dominio es su contenido y su acento de estado (franja/tinte), no su base. Espaciado: escala `space` (4/8/12/16/20/24/32); entre bloques de página siempre `mb-4` (16) y 12 dentro de grillas (`CardGrid`). **Piso tipográfico**: ningún texto por debajo de 10 px (10 solo para etiquetas en mayúsculas; el texto que se lee, ≥ 11) y ningún gris más oscuro que `#7C8BA1` para texto (`#475569`/`#334155`/`rgba(255,255,255,.3)` no se leen sobre el fondo, contraste ~2.5:1). Botones de icono ≥ 36 px y con `accessibilityLabel`. Fuente de títulos/cifras: `'SpaceGrotesk-Bold'` (no `'Space Grotesk'`). Los colores del tema viven en `src/global.css` (`--color-pos-*`) y `colors` de `tokens.ts` es su espejo. La tarjeta KDS (`OrderCardKDS`) conserva su fondo oscuro a propósito (pantalla de cocina).

**Componentes UI** (`Frontend/components/ui/`): `Button`/`Badge` (entrada animada solo con `animated`), `PageHeader` (+`rightContent`), `PageContainer` (con `refreshControl`; ya hace scroll — no anidar otro `ScrollView` vertical dentro), `Card`, `Input`, `SearchInput`, `Icon`, `ConfirmModal`, `StatCard`, `ChipGroup`, `SegmentedControl`, `DataTable`, `Paginator` (toda paginación usa este), `DateRangeFilter`, `PosRefreshControl` (pull-to-refresh con el color del POS), `AnimatedOrb`, `DenominacionCounter` (único formulario de billetes con botones: cobro, cambio, gastos, ajustes; cada fila es `BillCounter`), `ConteoCajaGrid`/`EstadoCajaLista` (conteo de caja escrito a mano y estado de solo lectura, claves de `DenominacionesMap` con `coins` = pesos), `InlineError` (errores en caja roja; `states/ErrorState` es la versión pantalla completa), `LoadingState`, `Avatar`, `IconButton`, `SectionHeader`, `MethodFilterChips`, `CajaMovimientosWidget`, `AjusteCajaModal`. `PaymentSelectionModal` (en `components/orders/`) maneja cobro completo y abonos (`mode='partial'`). Tarjetas de orden: `ElapsedTimer`/`useMinutosDesde` (`components/orders/`). Hooks de pantalla en `Frontend/hooks/` (`use-consulta`, `use-debounced-value`, `use-cuentas-transferencia` — caché compartida de cuentas; invalidar con `invalidarCuentasTransferencia()` al editarlas —, `use-usuarios`, `use-inventario`…).

Formatters `Intl` hoisted a module level (no recrearlos por render).

## Convenciones de código

- **TypeScript estricto** — no usar `any` salvo donde sea inevitable.
- **Hooks personalizados** para lógica de pantalla compleja (`use-facturas.ts`, `use-facturas-pagos-screen.ts`…) — la lógica fuera de los componentes.
- **Formato** desde `@/src/shared`: `formatCurrency(n)` ("15.000", maneja negativos), `formatCOP(n)` ("$15.000" / "-$1.500"), `timeAgo(fecha, 'corto'|'largo')`, `formatCompactCurrency`. No crear formatters locales de moneda. Otras reglas únicas: `sumDenominaciones`/`BILLETES_COP` (conteos de caja; `'coins'` = pesos), `urgenciaOrden`/`tipoPedidoMeta`/`nombreVisibleOrden` (tarjetas de orden), `getRecargoSabor`, `getOrdenEstadoMeta` (colores de estado; `constants/estados.ts` deriva de ahí).
- **`getLocalDateString()`** de `src/shared/utils/dateRange` para la fecha local — evita desfases UTC vs Bogotá.
- Importar componentes UI desde `../../components/ui` (no `@/components`).
